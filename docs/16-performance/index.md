## 1. パフォーマンスを下げる典型

ダッシュボードの動作が遅くなる原因は、たいてい以下のいくつかが重なっています。

| パターン | 説明 | 影響 |
|----------|------|------|
| **高基数フィルター** | ユニーク値が数万〜数十万あるフィールドのフィルター | クエリ・UI ともに重くなる |
| **巨大ビュー** | 1 つのシートで数万マークを描画 | レンダリングが重くなる |
| **シート数の多いダッシュボード** | 1 ダッシュボードに 10 枚以上のシート | 並列クエリと描画でメモリを圧迫 |
| **重い計算フィールド** | 巨大な IF 連鎖、表計算+LOD のネスト、文字列処理の多用 | クエリ実行時間が延びる |
| **ライブ接続 + 重い DB** | リモート DB へのライブ接続が応答遅延 | 1 操作ごとに数秒待ち |
| **巨大な画像オブジェクト** | 高解像度 PNG/JPG をそのまま埋め込み | 初期ロードが遅い |
| **「クイックフィルター」の多用** | 同一ダッシュボードに多数のクイックフィルター | 各フィルターが値リスト取得クエリを発行 |

::: tip 「遅い」と感じたら最初に切り分ける
原因は大きく「**データソース側**（DB/抽出のクエリが遅い）」「**ビュー側**（描画が遅い）」「**ダッシュボード側**（シート数・サイズ）」の 3 層に分けられます。後述のパフォーマンスレコーダーで、どこに時間がかかっているかを最初に見極めましょう。
:::

---

## 2. パフォーマンスレコーダーの使い方

Tableau Desktop には **パフォーマンスレコーダー** が組み込まれており、操作中のクエリ実行時間・コンパイル時間・描画時間を計測してレポート化できます。

### 起動手順

1. メニュー「**ヘルプ**」 → 「**設定とパフォーマンス**」 → 「**パフォーマンスの記録を開始**」
2. 計測したい操作（ダッシュボードを開く・フィルターを動かす など）を実行
3. 同じメニューから「**パフォーマンスの記録を停止**」
4. 自動でレポートワークブックが開く

### レポートの読み方

レポートには「**パフォーマンスの概要**」と「**詳細**」が含まれます。

| イベント種別 | 意味 |
|--------------|------|
| クエリの実行 | データソースに対するクエリ実行 |
| クエリのコンパイル | クエリの生成・最適化 |
| ジオコーディング | 地理情報の処理 |
| 接続 | データソースへの接続オープン |
| レイアウトのコンピューティング | ビューレイアウトの計算 |
| 抽出の生成 | 抽出ファイルの作成・更新 |

棒の長いイベントが「ボトルネック」です。クエリが遅いならデータソース/計算の見直し、レイアウトが遅いならシート数/マーク数の削減、というように対策が分かれます。

## 3. 抽出最適化

ライブ接続より**抽出 (.hyper)**の方が高速なケースが大半です。さらに抽出には「サイズを減らして高速化する」ためのオプションが揃っています。

### 列削減（不要列を捨てる）

データソースタブで使わない列を「**非表示**」にしておき、抽出時に「**非表示フィールドを除外する**」を有効にすると、抽出ファイルからその列が完全に削除されます。

| 効果 | 説明 |
|------|------|
| ファイルサイズ縮小 | 列数が減ればストレージ・メモリも減 |
| 抽出時間短縮 | 取り込む列が減るぶん速い |
| クエリ高速化 | 必要な列だけスキャンする |

### フィルター抽出（行を減らす）

抽出のダイアログで「**フィルター**」を追加し、たとえば「2023 年以降のみ」「特定地域のみ」を指定します。直近期間しか分析しないなら、抽出には過去データを含めない方が高速になります。

### 集計抽出

「**可視ディメンションのデータを集計**」をオンにすると、ビューで使うレベルまで事前に集計した抽出ができます。明細データが不要で、月次・カテゴリ別の集計値だけで足りる場合に非常に強力です。

```
（例）抽出を「年/月 × 会社 × 支払方法」で事前集計
→ 行レベル明細の数百万行が、数千行に圧縮される
```

::: warning 集計抽出のトレードオフ
集計抽出すると行レベルの明細はもう参照できません。「明細表」シートを併用するダッシュボードでは集計抽出は適さないことが多いです。
:::

### 増分更新

「**増分更新**」を設定すると、毎回フル再抽出せず、特定キー（例: `trip_start_timestamp`）の新規分だけを追加できます。日次更新で抽出時間を短縮できます。

## 4. 計算の最適化

計算フィールドの書き方ひとつで、クエリ性能が大きく変わります。

### CASE と IF

長い条件分岐は **CASE** の方が一般に高速とされます。CASE は値の一致判定だけなのに対し、IF は任意の条件式を扱う必要があるためです。

```
（推奨: CASE）
CASE [payment_type]
  WHEN "Cash" THEN "現金"
  WHEN "Credit Card" THEN "クレジット"
  ELSE "その他"
END
```

```
（IF を使う場合: 範囲・複合条件など CASE で書けないとき）
IF [trip_miles] < 1 THEN "短距離"
ELSEIF [trip_miles] < 5 THEN "中距離"
ELSE "長距離"
END
```

### ブール化

「文字列を等価判定する」より「ブールを返す」方が高速です。

```
（遅め）
IF [payment_type] = "Cash" THEN "現金" ELSE "その他" END

（推奨: ブール化）
[payment_type] = "Cash"
```

ブールで持ち、表示用ラベルだけ別計算で作るとさらに整理されます。

### 計算は集計の外に出す

```
（非効率: 各行で計算してから集計）
SUM(IF [payment_type] = "Cash" THEN [trip_total] ELSE 0 END)

（推奨: 同等だが、コンパイラが最適化しやすい）
SUM(IIF([payment_type] = "Cash", [trip_total], 0))
```

明確な性能差が出るとは限りませんが、**集計関数の外側に計算を出せる場合は出す**のが原則です。

### 長い IF は分割

`ELSEIF` が 10 個 20 個と続く計算は、可読性も性能も悪化します。グループや LOOKUP テーブル、データソース側のマッピングを検討してください。

::: tip 「不要な計算は作らない」が最強
最大の最適化は「最初から余計な計算フィールドを作らない」ことです。元データに同じ意味の列があるなら、計算で再生成せずに元の列を使いましょう。
:::

## 5. 表計算 vs LOD vs 行レベル計算のコスト感

3 種類の計算は、計算負荷が大きく違います。

| 種類 | コスト感 | 実行場所 |
|------|----------|----------|
| 行レベル計算 | 軽い | データソース側のクエリで処理可 |
| 集計計算（SUM など） | 軽い | データソース側 |
| **LOD 計算** (FIXED/INCLUDE/EXCLUDE) | 中〜重 | データソース側のサブクエリ |
| **表計算** (WINDOW_SUM など) | 軽め | ビュー描画時に Tableau 側で計算 |
| **複数の LOD のネスト** | 重い | サブクエリの多層化 |

### 使い分けの目安

- まずは **行レベル + 集計** で済むか考える
- 「総売上に対する各社のシェア」のように「異なる粒度の集計」が必要なら **LOD**
- 「累計売上」「移動平均」のように「ビューに並んでいる順序」が必要なら **表計算**
- LOD と表計算の両方で書けるなら、表計算の方が軽いことが多い

::: info 表計算は描画時計算
表計算はクエリ結果が返ってきた後にビュー上で計算されます。クエリは軽いが、マーク数が多いと表計算自体が重くなることがあります。
:::

## 6. ダッシュボードの最適化

ダッシュボードの遅さは、シート単体の遅さの合算より大きくなることがあります。並列クエリ・レイアウト計算・スクロール処理など、ダッシュボード固有のコストがあるためです。

### チェックリスト

- **シート数を絞る**: 1 ダッシュボードあたり 4〜6 枚程度を目安に
- **マーク数を抑える**: 1 ビューで数千〜1 万マークが上限の目安
- **クイックフィルターを減らす**: フィルターは「**関連する値のみ**」より「**すべての値**」の方が軽いことがある
- **画像を最適化**: PNG/JPG は表示サイズに合わせて事前にリサイズ
- **固定サイズで作る**: 自動/レンジは再レイアウトのコストがかかる
- **ダッシュボード起動時に非表示のシートを置かない**: 「**表示しない**」設定のシートも、初期ロード時にクエリが走る場合がある

### フィルターの「コンテキストフィルター」

「**コンテキストに追加**」したフィルターは、他のフィルターより先に評価される一時テーブルになります。フィルター後のデータ量が大幅に減るケースでは、後続クエリが軽くなることがあります。ただし、コンテキストフィルターの作成自体にコストがあるため、効果が出るのは「フィルター後のデータ量が大きく減る場合」に限られます。

## 7. 命名規約・整理術

性能とは少し違うトピックですが、長期保守性に直結する**整理術**を紹介します。

### フォルダで分類

データペインのフィールドを右クリック → 「**フォルダー**」 → 「**フォルダーの作成**」で、フィールドをグループ化できます。

- 「日付」「金額」「地理」「ID」「計算: KPI」「計算: フラグ」など意味で分ける
- 計算フィールドは「計算」フォルダにまとめると、元データ列との区別が明確に

### 命名規約

- 計算フィールドはプレフィックスで分類: `KPI_`、`Flag_`、`LOD_`、`Calc_` など
- パラメーターは `p_` プレフィックスで「明らかにパラメーター」と分かるように
- セットは `Set_` で
- 一時的なテスト用は `tmp_` を付け、本番反映時に削除

### コメントを書く

計算フィールドの編集画面の最初に `// 何のための計算か / 入力前提 / 更新履歴` をコメントで書きます。

```
// 売上のしきい値超え判定。
// パラメーター [料金しきい値] と比較。
// 2024-03-15 渡会 作成
[trip_total] >= [料金しきい値]
```

### 色のルールを決める

- KPI で使う色（例: ブランドカラー）
- 警告・注意（赤・橙）
- 中立（グレー）

カラーパレットを「**カスタムパレット**」として `Preferences.tps` に登録しておけば、全ワークブックで再利用できます。

::: tip 「他人が来月触れるか」テスト
3 ヶ月後の自分が、または別のメンバーが、ワークブックを開いて 30 分以内に構造を理解できるか想像してみましょう。理解できないようならフォルダ分け・命名・コメントを追加するサインです。
:::

## やってみよう

Chicago Taxi の大規模抽出に対して、最適化の手順を実践します。

1. **計測のベースラインを取る**
   - 大きめのダッシュボード（複数シート）を開く前に、メニュー「ヘルプ」 → 「設定とパフォーマンス」 → 「パフォーマンスの記録を開始」を実行。
2. **ダッシュボードを開いて閉じる**
   - 開き終わったら「パフォーマンスの記録を停止」。レポートで「クエリの実行」と「レイアウトのコンピューティング」のどちらが長いか確認。
3. **不要列の非表示**
   - データソースタブで、使っていない列（例: `taxi_id`、`tolls`、`extras` など演習で使わないもの）を非表示にする。
4. **抽出のフィルターを設定**
   - データソース → 抽出 → 編集 → 「フィルター」追加で、`trip_start_timestamp` を 2023 年のみに限定（既に 2023 年のみなら別期間で実験）。
5. **抽出を再生成して比較**
   - 抽出を再生成し、ファイルサイズが減ったことを確認。
6. **計算フィールドの最適化**
   - 既存の長い IF を CASE に書き直せるものは書き直す。等価判定の文字列ラベルはブール化。
7. **再度パフォーマンス記録**
   - 同じ操作を再実行し、クエリ時間が短縮されたか確認。
8. **データペインの整理**
   - フォルダを「日付」「金額」「地理」「計算」など作成し、フィールドを移動。命名規約も整える。

## まとめ

- パフォーマンス問題は「データソース」「ビュー」「ダッシュボード」の 3 層で切り分けるのが基本です。
- **パフォーマンスレコーダー**で計測してからチューニングを始めることで、効果のある箇所に手を入れられます。
- 抽出は「**列削減 / 行フィルター / 集計抽出 / 増分更新**」で大幅に軽くできます。
- 計算は **CASE > IF**、**ブール化**、**集計の外に出す** といった基本セオリーで改善します。
- ダッシュボードは「シート数を絞る」「画像を最適化」「固定サイズ」「フィルターを減らす」が効きます。
- フォルダ分け・命名規約・コメントなどの整理術は、長期保守性に直結します。
